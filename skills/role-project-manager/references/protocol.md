# 协作公共规则（v1）

所有 role-* 角色开始工作和交接前阅读本文件；报告正文可补充本领域内容，但不可省略公共字段。

## 人工决策
- 需求、方案、优先级、任务计划、接口契约、验收标准与最终验收由人工决定。角色负责分析、建议和执行已批准工作。
- 已批准范围内的实施与验证继续执行，不为同一授权反复请求确认；不得以默认值补充未批准的业务规则。
- 需要决定时列出问题、选项、推荐方案、理由及影响；集中提交，等待期间继续不依赖该决定的已批准工作。
- 批准记录保存到 docs/project/decisions.md，包含确认人、时间、原始确认来源、对象版本与适用范围。不得替人工生成批准记录；审批过期或版本变化时核对适用性。
- 测试改动仍遵守现有保护钩子与合并检查，不因本规则而绕过。

## 公共交接格式
首行固定为状态，后续使用下列字段；无内容填“无”，无法确定填“未知”并解释。

状态：待开始 / 进行中 / 待审查 / 待人工决定 / 待验收 / 已验收 / 已中止
任务：ID、标题（规划前可用功能 ID）
依据：spec 版本、契约版本、实现提交 SHA；未提交时标记工作区并附 diff，不能作为最终验收版本
产出：文件、PR、报告链接
验证：AC 编号、方法、实际结果、证据位置
问题：已知缺陷、未验证项、阻塞原因
决策请求：问题、选项、推荐及影响；无则填无
下一步：建议动作、接收角色、前置条件

角色原有的计划、实现报告和清单作为公共交接后的附件，不另设“完成”“可以继续”等首行。
审查附件的结论使用“通过 / 需修改 / 无法验证”，与任务状态分开。

## 状态与记录
- 项目管理维护 docs/project/tasks.md，其他角色提交交接报告，避免多人同时修改账本。
- 执行完成进入待审查；审查通过且证据齐全进入待验收；只有人工确认后进入已验收。
- 审查发现问题且修复已获授权时进入进行中；涉及新决定时进入待人工决定。
- 阻塞任务记录所缺决定或证据；中止须有人工决定，不能因无响应自行中止。
- 看板是任务账本的映射：待开始→待办，进行中→进行中，待审查→审查中，待人工决定/待验收→待确认，已验收→已完成；已中止另设状态并保留原因，不映射为完成。
- docs/project/decisions.md 是批准记录；spec 与 api-index 是业务与契约依据；看板与聊天内容不得覆盖这些依据。冲突时记录差异并提交人工决定。

## 版本与证据
- 每条验收标准有稳定 AC 编号、预期行为和验证方法（自动测试、人工操作或测量）。
- 证据记录提交 SHA、环境、时间、执行者、命令或操作步骤、预期和实际结果、日志/CI/截图位置。
- 结果使用通过 / 失败 / 未验证 / 不适用；不适用必须注明人工批准依据。
- 执行者提供初次证据，审查者独立执行相关验证；无法运行时写明缺口，不报告通过。
- 截图用于可见行为，不能替代接口、异常路径和性能验证。命令成功也不能替代覆盖检查。
- 代码变化后重新验证受影响 AC；新 SHA 不直接沿用旧版通过结论。保留历史证据。
- 禁止将密钥、令牌、用户隐私写入日志或截图；引用证据时保留必要上下文。

## 多会话交接
- 项目管理维护协调分支并登记已批准 spec/契约的提交 SHA。负责人提出文档补丁，经人工批准后纳入协调分支。
- 各 worktree 通过正常 Git 提交同步同一批准版本（按项目约定 merge 或 cherry-pick），核对内容和原始批准提交；文件同名不代表内容相同。
- 合并冲突、待提交修改或版本不一致时，停止依赖该契约的执行并报告，不覆盖其他 worktree。
- 无跨会话调用工具时，输出可转交的报告及下一步指令，由人工转交；不得声称已派发或已通知。
