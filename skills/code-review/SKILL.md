# 代码评审（v1）

一直生效的工程原则在基底层 AGENTS.md；仓库根目录 AGENTS.md 里有评审重点时以它为准。

## 步骤

1. 确定范围：`git diff main...HEAD`（或用户指定的 PR、提交范围）。先读提交信息和 docs/plans 里的计划，弄清改动意图。
2. 逐个文件读改动，必要时读调用方和被调用方，不只看 diff 片段。
3. 按下面的清单检查。
4. 跑一遍测试（`go test ./...`、`pytest` 等），把结果写进报告。
5. 输出问题清单。**不直接改代码**，由人决定改不改。

## 检查清单

- **正确性**：逻辑是否实现了意图；条件、循环边界、返回值是否正确。
- **边界情况**：空输入、单元素、最大值、溢出、重复元素、负数、Unicode。
- **错误处理**：错误是否被处理或向上返回；有没有被吞掉；资源是否释放。
- **并发**：共享状态、竞态、死锁、goroutine 泄漏（涉及时）。
- **可读性**：命名、函数长度、重复代码、注释是否说明“为什么”。
- **测试**：改动的行为是否有测试覆盖；测试是否真的断言了结果。
- **范围**：有没有与任务无关的改动、新依赖、调试残留。

工具能查的（格式、lint）不在评审里重复，除非工具没跑。

## 输出格式

```
## 评审结论
一句话：可以合并 / 改完再合并 / 需要重做。

## 问题
### 严重（会导致错误结果、崩溃或数据问题）
- path/to/file.go:42 —— 问题描述。触发条件：……。建议：……。

### 一般（边界、错误处理、测试缺失）
- ……

### 建议（可读性、风格，可不改）
- ……

## 已验证
- 测试命令与结果。
- 没检查到的部分。
```

没有问题的级别写“无”。每条问题都要有文件和行号；说不出触发条件的问题放进“建议”，不要放进“严重”。
