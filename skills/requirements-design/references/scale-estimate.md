# 规模估算

规模估算属于项目级内容，写入仓库根目录的 AGENTS.md，项目启动时编写，此后仅在功能改变规模时更新。其作用是判断是否需要引入缓存、消息队列或分布式架构，以避免过度设计。

## 估算表

| 指标 | 估算值 | 依据 |
|------|--------|------|
| DAU | | |
| 读 QPS（峰值） | | |
| 写 QPS（峰值） | | |
| 并发连接数 | | |
| 存储（一年） | | |
| 带宽（峰值） | | |
| 大模型 token（日） | | |

每项数值须注明来源是假设还是实测。个人项目、演示项目以假设为主，写明假设条件即可，不追求精确。

## 推算方法

- 峰值 QPS ≈ DAU × 人均日请求数 ÷ 86400 × 峰值系数（通常取 2 至 5）
- 存储 ≈ 日新增记录数 × 单条记录大小 × 365
- 并发连接数：仅在存在长连接（SSE、WebSocket）时估算，约等于同时在线用户数 × 人均连接数
- 大模型 token（日）≈ 日调用次数 ×（平均输入 token + 平均输出 token）；成本按所用模型的单价换算

各功能的计算、网络、存储开销在 spec 的"资源开销估算"表中估算，汇总后与本表对照。

## 架构判断

| 问题 | 引入前须满足的条件 |
|------|--------------------|
| 是否引入缓存 | 存在明确的读热点，且数据库已无法满足读 QPS 或延迟要求 |
| 是否引入消息队列 | 存在耗时的异步任务，或写入存在需要削峰的突发流量 |
| 是否采用分布式 | 单机的计算、存储或连接数已接近上限，或有明确的高可用要求 |

不满足上述条件时，在 AGENTS.md 中写明"不引入"及理由。说明不需要某项技术的理由，与说明需要它的理由同样重要。

## 结论写法

```
结论：单机部署加 SQLite 可满足需求，不引入缓存与消息队列，不采用分布式架构。
理由：写 QPS 估算低于 10，并发连接数低于 100，均为假设值；如实测超出，重新评估。
```
