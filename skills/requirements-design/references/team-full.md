# 协作档位：完整

适用于前后端需要并行开发、接口契约存在多方依赖、涉及并发或缓存等需要专项审查的功能。

## 分层架构

采用分层与领域正交的结构：纵向按层级划分，横向按领域（前端、后端）划分。

1. **产品经理**：由开发者与 agent 共同担任。agent 起草初稿，开发者审核定稿，需求变更亦共同商定。定稿后由 agent 下发给前后端负责人，并作为前后端之间的协调方。
2. **项目管理**：仅负责跟踪进度。小型项目可省略，由看板替代。
3. **前端负责人 / 后端负责人**：后端负责人补充 API 设计和数据模型，前端负责人提出界面需求，双方交互一轮后提交开发者审核；审核通过后将本领域的工作交给规划者。
4. **规划者 → 执行者 → 审查者**：规划者拆分任务并编写测试，执行者负责实现，审查者负责把关；后端专项审查按需启用。

## 角色总表

| 角色 | 层级 | 领域 | 担任者 | 职责 | 禁止事项 |
|------|------|------|--------|------|----------|
| 产品经理 | 一 | 全局 | 开发者与 agent：agent 起草，开发者审核 | 商定需求与变更，定稿后下发，协调前后端 | 未经开发者审核不得下发，不得自行确定需求 |
| 项目管理（可选） | 一 | 全局 | 小型项目可省略 | 跟踪进度 | 不修改需求与代码 |
| 前端负责人 | 二 | 前端 | 强模型 | 审阅 API 与数据模型，提出前端需求，编排前端任务 | 不直接修改 API 与数据模型 |
| 后端负责人 | 二 | 后端 | 强模型 | 补充 API 设计与数据模型，维护接口影响索引与 mock，编排后端任务 | 接口契约变更须经开发者批准 |
| 前端规划者 | 三 | 前端 | 强模型 | 按组件、状态、交互拆分任务，编写验收测试 | 不编写实现代码 |
| 后端规划者 | 三 | 后端 | 强模型 | 按接口、数据模型、业务逻辑拆分任务，标注所需专项审查 | 不编写实现代码 |
| 前端 / 后端执行者 | 四 | 前端 / 后端 | 执行模型 | 按任务实现功能，使测试通过 | 不修改测试，不超出任务范围 |
| 前端 / 后端审查者 | 四 | 前端 / 后端 | 另一个 agent | 审查测试覆盖与代码质量 | 只提出问题，不修改代码 |
| 后端专项审查 | 四 | 后端细分领域 | 按需启用 | 分别审查数据库、缓存、并发与流式、接口与安全 | 仅审查本专项 |

## 后端专项审查

以审查者身份参与，仅在任务涉及相应领域时启用，以免 agent 过多导致信息在逐层传递中丢失：

- **数据库**：表结构、索引、事务边界、N+1 查询、外键与级联
- **缓存（Redis）**：Lua 脚本原子性，缓存雪崩、穿透、击穿的防护，缓存与数据库的一致性
- **并发与流式**：锁与加锁顺序、goroutine 泄漏、SSE 断开处理、超时
- **接口与安全**：资源归属校验、输入限制、幂等性
