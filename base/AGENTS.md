# 基底层规则

所有仓库、所有助手（Claude Code、Codex、pi）共用。仓库根目录的 AGENTS.md 补充项目细节，两者冲突时以仓库层为准。

## 工作方式

- 先读懂再动手：改代码前先看相关文件和已有测试，沿用仓库现有的命名、结构和写法。
- 需求不清楚时先问，或说明你采用的理解再继续。
- 复杂任务先把计划写进 docs/plans/<任务名>.md，接手的人先读它。
- 只做被要求的改动，不顺手重构、不加没被要求的功能。

## 代码

- 可维护优先：命名清晰，函数短小，一个函数做一件事。
- 不过度设计：不为想象中的需求加抽象、配置项或扩展点。
- 错误要处理或明确向上返回，不吞掉错误。
- 注释写“为什么”，不写“做了什么”。
- 不引入新依赖，除非先说明理由并得到同意。

## 测试与检查

- 改动行为就要有测试覆盖；修 bug 先写能复现的测试。
- 交付前在本地跑通格式化、lint 和测试，并报告实际结果；失败就如实说明。
- 格式、lint 这类工具能检查的事交给工具，不靠记忆。

## Git

- 不得推送到 main，只在功能分支上工作，通过 PR 合并。
- 不得用 --no-verify 或其他方式跳过钩子；钩子失败就修问题。
- 不改写已推送的历史，不强制推送共享分支。
- 一个提交只做一件事，提交信息说明改了什么、为什么。

## 多助手协作

- 两个助手不在同一个工作目录里同时改代码；需要并行时用 git worktree 各开一个目录。
- 接力时以提交为交接点：实现方提交后，审查方只审这个分支相对 main 的改动。
- 审查只给按严重程度分级的问题清单，不直接改代码，由人决定改不改。

## 安全

- 密钥、令牌、账号信息不写进代码、配置、提示词或提交记录，只用环境变量引用。
- 删除文件、推送代码、安装依赖前先确认。
- 能用命令行工具（git、gh、go）完成的事，不额外调用 MCP。

## 输出

- 回答先给结论，再给依据。
- 说明改了哪些文件、怎么验证的；没验证的地方明确说没验证。
