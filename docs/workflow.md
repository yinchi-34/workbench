# AI 协作开发工作流（通用版）

每个新功能都按这套流程走。目标有两个：让 AI 快速产出代码；每一步都有办法验证 AI 的产出，不盲信。

## 第一步：需求设计

文档分两层：项目级一份，每个功能一份。

| 文档 | 范围 | 什么时候写 | 内容 |
|------|------|------------|------|
| AGENTS.md（项目层） | 整个项目的大框架 | 项目开始时写，之后很少改 | 技术栈、目录结构、规模估算、全局规则 |
| docs/specs/<功能名>.md | 只管当前这个功能 | 每个新功能开发前写 | 系统设计、对规模的影响、API 设计、数据模型 |
| docs/api-index.md | 全部接口 | 每个功能定稿后同步更新 | 接口影响索引（见第二步） |

### 1. 项目级：规模估算（写进 AGENTS.md）

| 指标 | 估算值 | 依据 |
|------|--------|------|
| DAU | | |
| 读 QPS（峰值） | | |
| 写 QPS（峰值） | | |
| 并发连接数 | | |
| 存储（一年） | | |
| 带宽（峰值） | | |

每个数值都写明是假设还是实测。这张表用来判断要不要上缓存、消息队列、分布式，避免过度设计。

### 2. 功能级：spec（docs/specs/<功能名>.md）

每个功能一份，模板见 [templates/fullstack/docs/specs/_template.md](../templates/fullstack/docs/specs/_template.md)：

- **系统设计**（产品经理写）：功能需求、非功能需求、不做的事、验收标准
- **对规模的影响**：会不会改变 AGENTS.md 里的估算；会的话同步更新
- **API 设计**、**数据模型**（后端负责人补）：每个字段写理由，写清按当前规模要不要考虑分布式
- **前端反馈**（前端负责人写）：界面和交互需要的额外字段或格式

### 3. 新功能调研（技能，按需使用）

只有以前没做过的功能才调研，用 tech-research 技能：列出 3 到 5 种做法，从技术栈匹配度、规模适配度、实现成本三个维度比较，给出倾向。

调研结果出来后，我和另一个模型一起讨论（交叉验证，避开同一个模型的盲区），定下方案，再交给产品经理写进 spec。

### 4. 大致框架与测试先行

由产品经理、前端负责人、后端负责人一起做，不是哪一个角色单独定：

- 把功能拆成几个阶段，每个阶段都能单独跑通、单独验证
- 每个阶段先定下关键测试用例，作为后面的验收标准

**完成标准**：spec 里每一项取舍都写了理由；验收标准覆盖了全部功能需求；我已经审核确认。

## 第二步：任务拆分与多 agent 协作

1. 每个阶段按前端和后端拆成小任务。每个任务写清楚怎么做、改哪些文件、验收测试是什么。
2. **按模型强弱分工**：强模型负责分析、拆任务、审查；执行模型负责实现。
3. **测试先行**：规划者把验收测试写成测试文件，执行者只负责让它通过。
4. **交叉审查**：测试本身也要审。写代码的 agent 不能自己审自己。

### 分层架构

纵向按层级，横向按领域（前端、后端），两者正交。

1. **产品经理**：我和 agent 一起担任。agent 出初稿，我审核定稿，需求变更也一起商量。定稿后由它下发给前后端负责人，也是前后端沟通的桥梁。
2. **项目管理**：只跟进度，小项目可以省掉，由看板代替。
3. **前端负责人 / 后端负责人**：后端补 API 设计和数据模型，前端提界面需求，两边交互一轮后交我审核；再把本领域的工作交给规划者。
4. **规划者 → 执行者 → 审查者**：规划者拆任务、写测试，执行者实现，审查者把关；后端专项审查按需启用。

### 角色总表

| 角色 | 层级 | 领域 | 谁来担任 | 职责 | 不能做的事 |
|------|------|------|----------|------|------------|
| 产品经理 | 一 | 全局 | 我 + agent：agent 出初稿，我审核 | 商量需求和变更，定稿后下发，协调前后端 | 没经过我审核不能下发，不能自己定需求 |
| 项目管理（可选） | 一 | 全局 | 小项目省掉 | 跟踪进度 | 不改需求和代码 |
| 前端负责人 | 二 | 前端 | 强模型 | 审 API 和数据模型，提前端需求，编排前端任务 | 不直接改 API 和数据模型 |
| 后端负责人 | 二 | 后端 | 强模型 | 补 API 设计和数据模型，维护接口索引和 mock，编排后端任务 | 契约变更要我批准 |
| 前端规划者 | 三 | 前端 | 强模型 | 按组件、状态、交互拆任务，写验收测试 | 不写实现代码 |
| 后端规划者 | 三 | 后端 | 强模型 | 按接口、数据模型、业务逻辑拆任务，标出专项 | 不写实现代码 |
| 前端 / 后端执行者 | 四 | 前端 / 后端 | 执行模型 | 按任务实现，让测试通过 | 不改测试，不超出任务范围 |
| 前端 / 后端审查者 | 四 | 前端 / 后端 | 另一个 agent | 审测试覆盖和代码质量 | 只提问题，不改代码 |
| 后端专项审查 | 四 | 后端细分 | 按需启用 | 数据库、缓存、并发与流式、接口与安全，各审一块 | 只审自己那一块 |

后端专项主要当审查者，任务用到哪块才启用哪块，避免 agent 太多、信息层层传下去丢失：

- **数据库**：表结构、索引、事务边界、N+1 查询、外键与级联
- **缓存（Redis）**：Lua 原子性，雪崩、穿透、击穿的防护，缓存和数据库的一致性
- **并发与流式**：锁和加锁顺序、goroutine 泄漏、SSE 断开处理、超时
- **接口与安全**：资源归属校验、输入限制、幂等性

### 看板

先用 GitHub Projects，以后再看要不要换。

- 列：待办、进行中、审查中、等我确认、已完成
- 每张卡片对应一个任务，链接到它的 spec 和任务说明
- 卡片状态由负责人会话随流程更新；碰到"需要确认"的报告，移到"等我确认"

### 接口变更规则

- 先判断变更原因：只为 UI 改，就只改前端；涉及流程逻辑，或者要新增字段、ID，前后端同步改。
- 接口契约（spec 的 API 设计 + docs/api-index.md）是唯一依据，两边都以它为准，不各自改。
- 变更由产品经理提出，我批准后同时下发两边。后端先更新契约和 mock，前端照着契约并行开发。

### 接口影响索引

借鉴 RBAC 的分层判断：接口按层级管理，改动一个接口前，AI 先查索引弄清会牵连到哪里，再动手。模板见 [templates/fullstack/docs/api-index.md](../templates/fullstack/docs/api-index.md)。

- **层级**分三种：对外接口、内部接口、基础能力。层级越低，被依赖得越多，改动风险越高。
- **改动规则**：改一个接口时，"谁依赖它"一栏的每一项都要检查，写进影响说明。牵连到对外接口的，按契约变更处理，必须我批准。

### 人工审核关口（HITL）

下面这些节点必须停下来等我确认：

1. 需求确认：spec 定稿
2. 接口契约变更
3. 任何对测试文件的修改
4. 同一个问题连续失败两次
5. 最终验收

## 第三步：出错处理

1. **问题记录**：每遇到一个问题就记下：AI 给了什么、我怎么发现不对、怎么修的。边做边记，放进业务仓库的 docs/notes/。
2. **测试一直不过**：测试文件只有我同意才能改，防止 AI 放宽断言或跳过测试；同一个问题连续失败两次就停下来，转人工审核。
3. **代码可追溯**：执行者报告里写明哪行代码对应哪个功能点，我再整体抽查。
4. **沉淀**：通用的坑加进 workbench 的常见问题清单，同步升级相关角色的 prompt。

## 第四步：收尾验收三步法

1. **看测试**：流程完整，覆盖需求，全部通过。
2. **实际操作**：自己亲手把功能用一遍，包括异常路径。
3. **按常见问题清单逐项检查**。

## Prompt 版本管理

每个角色 prompt 标版本号（标题里的 v1、v2），在 CHANGELOG.md 里写修改原因。踩到新坑、清单更新时，同步升级相关角色。
