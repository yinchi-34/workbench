# AI 协作开发工作流（通用版）

本流程适用于每一个新功能的开发，目标有两项：一是借助 AI 提高编码效率；二是在每个环节对 AI 的产出进行验证，避免未经核实即采用。文中"开发者"指使用本流程的人，负责审核与最终决策。

## 第一步：需求设计

设计文档分为项目级和功能级两层。

| 文档 | 范围 | 编写时机 | 内容 |
|------|------|----------|------|
| AGENTS.md（项目级） | 整个项目 | 项目启动时编写，此后很少修改 | 技术栈、目录结构、规模估算、全局规则 |
| docs/specs/<功能名>.md | 单个功能 | 每个功能开发前编写 | 系统设计、对规模的影响、API 设计、数据模型 |
| docs/api-index.md | 全部接口 | 每个功能定稿后同步更新 | 接口影响索引（见第二步） |

### 2. 功能级：spec（docs/specs/<功能名>.md）

每个功能对应一份 spec，模板见 [templates/fullstack/docs/specs/_template.md](../templates/fullstack/docs/specs/_template.md)：

- **系统设计**（产品经理编写）：功能需求、非功能需求、不做的事、验收标准
- **对规模的影响**：说明是否改变 AGENTS.md 中的估算；如有变化，同步更新
- **API 设计**、**数据模型**（后端负责人补充）：每个字段注明设计理由，并说明按当前规模是否需要考虑分布式
- **前端反馈**（前端负责人编写）：界面与交互所需的额外字段或返回格式

### 3. 新功能调研（技能，按需使用）

仅在开发此前未实现过的功能时进行调研，使用 tech-research 技能：列出 3 至 5 种实现方案，从技术栈匹配度、规模适配度、实现成本三个维度进行比较，并给出倾向性意见。

调研结果由开发者与另一个模型共同评审（交叉验证，以规避单一模型的盲区），确定方案后交由产品经理写入 spec。

### 4. 阶段划分与测试先行

阶段划分与验收测试由产品经理、前端负责人、后端负责人共同确定，不由单一角色决定：

- 将功能划分为若干阶段，每个阶段均可独立运行、独立验证
- 每个阶段开始前先确定关键测试用例，作为后续的验收标准

**完成标准**：spec 中的每项取舍均注明理由；验收标准覆盖全部功能需求；开发者已审核确认。

## 第二步：任务拆分与多 agent 协作

1. 每个阶段按前端、后端拆分为小任务，每个任务明确实现方式、涉及文件和验收测试。
2. **按模型能力分工**：能力较强的模型负责分析、拆分任务和审查；执行模型负责实现。
3. **测试先行**：规划者将验收测试写成测试文件，执行者的职责是使测试通过。
4. **交叉审查**：测试本身同样需要审查，编写代码的 agent 不得审查自己的产出。

### 分层架构

采用分层与领域正交的结构：纵向按层级划分，横向按领域（前端、后端）划分。

1. **产品经理**：由开发者与 agent 共同担任。agent 起草初稿，开发者审核定稿，需求变更亦共同商定。定稿后由 agent 下发给前后端负责人，并作为前后端之间的协调方。
2. **项目管理**：仅负责跟踪进度。小型项目可省略，由看板替代。
3. **前端负责人 / 后端负责人**：后端负责人补充 API 设计和数据模型，前端负责人提出界面需求，双方交互一轮后提交开发者审核；审核通过后将本领域的工作交给规划者。
4. **规划者 → 执行者 → 审查者**：规划者拆分任务并编写测试，执行者负责实现，审查者负责把关；后端专项审查按需启用。

### 角色总表

| 角色 | 层级 | 领域 | 担任者 | 职责 | 禁止事项 |
|------|------|------|--------|------|----------|
| 产品经理 | 一 | 全局 | 开发者与 agent：agent 起草，开发者审核 | 商定需求与变更，定稿后下发，协调前后端 | 未经开发者审核不得下发，不得自行确定需求 |
| 项目管理（可选） | 一 | 全局 | 小型项目可省略 | 跟踪进度 | 不修改需求与代码 |
| 前端负责人 | 二 | 前端 | 强模型 | 审阅 API 与数据模型，提出前端需求，编排前端任务 | 不直接修改 API 与数据模型 |
| 后端负责人 | 二 | 后端 | 强模型 | 补充 API 设计与数据模型，维护接口影响索引与 mock，编排后端任务 | 接口契约变更须经开发者批准 |
| 前端规划者 | 三 | 前端 | 强模型 | 按组件、状态、交互拆分任务，编写验收测试 | 不编写实现代码 |
| 后端规划者 | 三 | 后端 | 强模型 | 按接口、数据模型、业务逻辑拆分任务，标注所需专项审查 | 不编写实现代码 |
| 前端 / 后端执行者 | 四 | 前端 / 后端 | 执行模型 | 按任务实现功能，使测试通过 | 不修改测试，不超出任务范围 |
| 前端 / 后端审查者 | 四 | 前端 / 后端 | 另一个 agent | 审查测试覆盖与代码质量 | 只提出问题，不修改代码 |
| 后端专项审查 | 四 | 后端细分领域 | 按需启用 | 分别审查数据库、缓存、并发与流式、接口与安全 | 仅审查本专项 |

后端专项以审查者身份参与，仅在任务涉及相应领域时启用，以免 agent 过多导致信息在逐层传递中丢失：

- **数据库**：表结构、索引、事务边界、N+1 查询、外键与级联
- **缓存（Redis）**：Lua 脚本原子性，缓存雪崩、穿透、击穿的防护，缓存与数据库的一致性
- **并发与流式**：锁与加锁顺序、goroutine 泄漏、SSE 断开处理、超时
- **接口与安全**：资源归属校验、输入限制、幂等性

### 看板

暂时使用 GitHub Projects。

- 列：待办、进行中、审查中、待确认、已完成
- 每张卡片对应一个任务，并链接到对应的 spec 与任务说明
- 卡片状态由负责人会话随流程更新；收到首行为"需要确认"的报告时，将卡片移至"待确认"

### 接口变更规则

- 首先判断变更原因：仅因界面调整而变更的，只修改前端；涉及流程逻辑，或需新增字段、ID 的，前后端同步修改。
- 接口契约（spec 中的 API 设计与 docs/api-index.md）是唯一依据，前后端均以其为准，不得各自修改。
- 变更由产品经理提出，经开发者批准后同时下发前后端。后端先更新契约与 mock，前端依据契约并行开发。

### 接口影响索引

参照 RBAC 的分层判断思路：接口按层级管理，修改任一接口前，AI 须先查阅索引，明确受影响的范围后再进行修改。模板见 [templates/fullstack/docs/api-index.md](../templates/fullstack/docs/api-index.md)。

- **层级**分为三类：对外接口、内部接口、基础能力。层级越低，依赖方越多，修改风险越高。
- **修改规则**：修改接口时，须逐项检查"谁依赖它"一栏，并写入影响说明。涉及对外接口的，按接口契约变更处理，须经开发者批准。

### 人工审核节点（HITL）

以下节点须暂停流程，经开发者确认后方可继续：

1. 需求确认：spec 定稿
2. 接口契约变更
3. 对测试文件的任何修改
4. 同一问题连续两次未能解决
5. 最终验收

## 第三步：问题处理

1. **问题记录**：每遇到一个问题即时记录 AI 的输出、发现问题的方式及修复过程，存放于业务仓库的 docs/notes/。
2. **测试持续失败**：测试文件须经开发者同意方可修改，以防 AI 放宽断言或跳过测试；同一问题连续两次未能解决时，暂停并转入人工审核。该约束同时由工具执行：钩子禁止 agent 修改已有测试文件，merge.py 在合并时再次检查（见 fullstack 模板的"测试保护"一节）。
3. **代码可追溯**：执行者须在报告中注明代码行与功能点的对应关系，开发者据此进行整体抽查。
4. **经验沉淀**：通用问题补充至 workbench 的常见问题清单，并同步更新相关角色的 prompt。

## 第四步：收尾验收

验收分为三步：

1. **测试检查**：流程完整、覆盖全部需求、全部通过。
2. **实际操作**：由开发者亲自完整使用一遍功能，包括异常路径。
3. **清单检查**：按常见问题清单逐项核对。

## Prompt 版本管理

每个角色 prompt 均标注版本号（标题中的 v1、v2 等），修改原因记录于 CHANGELOG.md。发现新问题或清单更新时，同步升级相关角色的 prompt。
